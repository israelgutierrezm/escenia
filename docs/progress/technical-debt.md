# Technical Debt Register

Registrar deuda técnica conscientemente (descripción, motivo, impacto, prioridad, resolución propuesta).

| ID | Área | Descripción | Motivo | Impacto | Prioridad | Resolución propuesta | Estado |
|----|------|-------------|--------|---------|-----------|----------------------|--------|
| TD-001 | Tenancy | El `TenantScope` es fail-closed sólo en HTTP; en consola/queues no filtra si falta contexto. | Evitar romper seeders/factories/tests que crean datos sin request. | Un Job que consulte modelos tenant-owned sin `TenantContext::runFor(...)` podría leer cross-tenant. | Media | Al implementar Jobs con datos de tenant, propagar el `tenant_id` y envolver en `TenantContext::runFor`. Añadir tests de Job. | Abierta |
| TD-002 | Feature Flags | La unicidad de flags **globales** por `key` no está garantizada por índice. | MySQL trata múltiples `NULL` como distintos en un índice único; los owners (`tenant/workspace/user`) son nullable. | Posibles filas duplicadas de un flag global con la misma `key`. | Baja | Hacer upsert por `key+scope` en la capa de aplicación (o columna generada/sentinela cuando exista un servicio de flags). | Abierta |
| TD-003 | Infra | Redis no se usa operativamente en Foundation (cache/queue/session en `database`; cliente `predis`). | No introducir infraestructura antes de necesitarla; entorno local sin Redis. | Rendimiento/locks subóptimos hasta habilitar Redis en producción. | Media | Habilitar Redis (phpredis) para cache, queues, locks y rate limiting al desplegar. | Abierta |
| TD-004 | Frontend | `packages/ui` es mínimo (tokens + un componente). | Alcance de Foundation; sólo se requiere la base del design system. | Componentes se irán duplicando en apps hasta consolidar la librería. | Baja | Expandir el design system (tipografía, formularios, layout) al crecer las apps. | Abierta |
| TD-005 | Auth | Sanctum stateful cookie requiere mismo sitio/subdominios + CORS con credenciales en producción. | Autenticación first-party basada en cookies. | Configuración incorrecta de dominios/CORS rompería el login cross-origin. | Media | Documentar y fijar `SESSION_DOMAIN`, `SANCTUM_STATEFUL_DOMAINS` y `config/cors.php` por entorno; considerar tokens para el futuro Developer Platform. | Abierta |
| TD-006 | Events | Las sub-entidades de evento (`sessions`, `speakers`, `schedule`) exponen sólo create + list en la API. | Alcance de Fase 1 (Event Core); update/delete/reorder no eran imprescindibles. | Falta editar/eliminar/reordenar vía API hasta implementarlo. | Baja | Añadir update/delete/reorder cuando el Studio/agenda lo requiera. | Abierta |
| TD-007 | Studio/Media | Las llamadas `removeParticipant`/`closeRoom` a la RoomService API de LiveKit no se prueban contra infraestructura real. | Sin servidor LiveKit en el entorno; la suite usa el provider fake. | Fallos de teardown solo se detectarían en despliegue real (son best-effort y se loguean). | Media | Añadir tests de integración contra un LiveKit local (docker) o con `Http::fake` verificando el payload twirp. | Abierta |
| TD-008 | Studio | El canje de guest links single-use tiene una ventana TOCTOU (check `isRedeemable` + `increment` no atómicos). | Alcance de Fase 2; el riesgo es bajo (links suelen ser por persona). | Dos canjes simultáneos de un link single-use podrían ambos crear participante. | Baja | Incremento condicional atómico (`where uses < max`/`single_use`) o lock al canjear. | Abierta |
| TD-009 | Production | `scene_versions` es append-only sin retención: cada guardado crea una versión permanente. | Alcance de Fase 3; el versionado inmutable prioriza poder reabrir diseños. | Crecimiento ilimitado de versiones en escenas muy editadas. | Baja | Política de retención/poda (conservar N últimas + hitos) o snapshotting cuando se justifique. | Abierta |
| TD-010 | Broadcast | Los eventos críticos de broadcast (started/ended) se emiten como domain events, no vía Outbox (ADR-007). | Alcance de Fase 4; aún no hay consumidores externos (analytics/notifications). | Sin garantía transaccional de publicación cuando existan consumidores externos. | Media | Implementar el Outbox pattern (tabla `analytics_event_outbox` + dispatcher) para el lifecycle de broadcast. | Abierta |
| TD-011 | Broadcast/Media | `startEgress`/`stopEgress` de LiveKit no se prueban contra un servidor real; la suite usa el provider fake. | Sin infraestructura LiveKit en el entorno. | Fallos de egress solo se detectarían en despliegue real (best-effort, logueados). | Media | Tests de integración contra LiveKit local o con `Http::fake` verificando el payload de la Egress API. | Abierta |
